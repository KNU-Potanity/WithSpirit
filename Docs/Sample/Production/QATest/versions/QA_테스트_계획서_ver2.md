# QA / 테스트 계획서

## 0. 문서 목적

이 문서는 게임을 테스트할 때 **무엇을, 어떤 기준으로, 어떻게 보고할지**를 정리합니다.

- 지금은 혼자 핵심 기능을 테스트하는 단계지만, 나중에 동아리 부원들이 확장 기능을 추가하면서 버그가 늘어날 것을 대비해 **미리 양식과 기준을 정해두는 문서**입니다.
- 지금 당장 모든 항목을 채울 필요는 없고, 실제 버그가 생기기 시작하면 이 양식에 맞춰 기록하면 됩니다.

---

## 1. 테스트 범위

| 단계 | 테스트 대상 | 테스트 주체 |
|---|---|---|
| 1단계 (현재) | 핵심 기능 MVP (이동/점프/충돌/리스폰/목표/카메라) | 혼자 |
| 2단계 (이후) | 확장 기능 (적, 수집/보상, 파워업, UI/사운드 등) | 동아리 부원 각자 + 통합 테스트 |

---

## 2. 테스트 유형

| 유형 | 설명 | 예시 |
|---|---|---|
| 기능 테스트 | 의도한 대로 동작하는지 확인 | "가시에 닿으면 리스폰되는가" |
| 조작감 테스트 | 수치가 적절한지, 플레이했을 때 느낌이 좋은지 확인 | "점프 거리가 너무 빡빡하지 않은가" (`레벨디자인_MVP_스테이지_ver4.md` 6장 체크리스트 참고) |
| 통합 테스트 | 여러 기능이 같이 있을 때 충돌 없이 동작하는지 확인 | "적 시스템 추가 후에도 기존 리스폰 로직이 정상 동작하는가" |
| 회귀 테스트 | 새 기능 추가 후 기존 기능이 망가지지 않았는지 재확인 | "카메라 확장(자동 스크롤 옵션) 추가 후에도 기본 추적 모드가 정상인가" |

## 3. 핵심 기능(MVP) 테스트 케이스

`플랫포머_게임_기획서_MVP.md`의 완료 기준(DoD)을 테스트 케이스 형태로 풀어둔 표입니다.

| 번호 | 테스트 항목 | 테스트 방법 | 통과 기준 |
|---|---|---|---|
| T-01 | 좌우 이동 | 좌/우 입력 후 캐릭터 이동 확인 | 가속/감속이 `캐릭터컨트롤_스펙_MVP.md` 수치와 체감상 일치 |
| T-02 | 기본 점프 | 점프 버튼 입력 | 최대 높이 3타일 도달, 가변 점프(짧게/길게) 차이 확인 |
| T-03 | 코요테 타임 | 발판 끝에서 살짝 늦게 점프 입력 | 약 0.12초 이내면 점프 성공 |
| T-04 | 발판 충돌 | 발판 위 이동/정지 | 발판을 통과하거나 끼이지 않음 |
| T-05 | 즉사 장애물 | 가시/낭떠러지 접촉 | 즉시 리스폰 처리 |
| T-06 | 리스폰 | 사망 후 | 스테이지 시작 지점으로 정확히 복귀 |
| T-07 | 목표 지점 | 도착 지점 접촉 | 클리어 판정 발생 |
| T-08 | 카메라 추적 | 캐릭터 이동 | 좌우로 부드럽게 스크롤, 스테이지 경계에서 멈춤 |
| T-09 | 전체 플레이 | 시작 → 도착까지 1회 플레이 | 중간에 끊기거나 멈추는 구간 없이 완주 가능 |

## 4. 버그 리포트 양식 (GitHub Issue 기준)

GitHub Issue를 생성할 때 아래 템플릿을 사용합니다.

```
제목: [버그] 간단한 증상 요약

## 증상
무엇이 잘못되었는지 설명

## 재현 방법
1. ...
2. ...
3. ...

## 기대한 동작
원래는 어떻게 동작해야 하는지

## 실제 동작
실제로 어떻게 동작했는지

## 환경
- Unity 버전:
- 브랜치/커밋:

## 우선순위
Critical / Major / Minor (5장 기준 참고)

## 스크린샷 또는 영상 (선택)
```

> GitHub Issue에 `bug` 라벨을 붙이고, 가능하면 어떤 기능(예: `player-movement`, `camera`)과 관련된 버그인지 라벨이나 제목에 표시해두면 나중에 찾기 쉬워요.

---

## 5. 버그 우선순위 분류

| 우선순위 | 기준 | 예시 |
|---|---|---|
| Critical | 게임 진행이 불가능해짐 | 캐릭터가 바닥을 뚫고 떨어짐, 리스폰이 동작하지 않음 |
| Major | 핵심 기능은 동작하지만 의도와 다르게 동작 | 점프 높이가 스펙과 크게 다름, 카메라가 가끔 멈춤 |
| Minor | 플레이에는 큰 영향 없는 사소한 문제 | 이펙트 위치가 살짝 어긋남, 디버그 텍스트 오타 |

> Critical 버그는 발견 즉시 다른 작업보다 우선해서 수정합니다.

## 6. 확장 기능 테스트 가이드 (동아리 단계)

부원이 확장 기능을 추가할 때는 아래 순서를 따릅니다.

1. **개별 테스트**: 본인이 만든 기능만 단독으로 테스트 (예: 적 AI만 켜놓고 동작 확인)
2. **PR 생성 전 체크**: 핵심 기능(T-01~T-09)이 본인 기능 때문에 깨지지 않았는지 간단히 재확인
3. **PR 리뷰 시 확인**: 리뷰어가 코드뿐 아니라 실제 플레이도 한 번 해보고 머지
4. **통합 테스트**: 여러 확장 기능이 `develop`에 모이면, 전체를 한 번 플레이하며 기능 간 충돌 확인 (예: 파워업과 적 시스템이 같이 있을 때 문제 없는지)

## 7. 테스트 진행 시점

`일정_마일스톤_ver2.md`와 연결해서, 아래 시점에 테스트를 진행합니다.

| 시점 | 테스트 내용 |
|---|---|
| 핵심 기능 구현 완료 직후 | 3장의 T-01~T-09 전체 실행 |
| 레벨 적용 후 | 조작감 테스트 (난이도 체감 확인) |
| 확장 기능 머지 시마다 | 개별 테스트 + 회귀 테스트 |
| 최종 빌드 전 | 전체 통합 테스트 1회 |

## 8. 다음 단계

- 핵심 기능 구현이 끝나면, 3장의 테스트 케이스(T-01~T-09)를 직접 체크하며 통과 여부 기록
- 버그가 발견되면 4장 양식대로 GitHub Issue 생성
- 확장 기능 단계가 시작되면, 부원들에게 6장 가이드 공유
