# 문서 작성 가이드라인

이 문서는 BasePlatformer 프로젝트의 `Docs/` 폴더에 문서를 작성/관리할 때 따라야 할 공통 규칙을 정의합니다.
대상은 프로그래밍/기획/아트 모든 역할이며, 본 가이드라인의 오너는 **프로젝트 매니저(PM)** 입니다.

> 마지막 수정일: 2026-09-14 — 문서별 `versions/` 폴더를 통한 버전 관리를 폐지했고, MVP 스냅샷 아카이브였던 `Docs/Sample/` 폴더도 삭제했습니다. 과거 내용은 모두 GitHub 커밋 히스토리로 확인합니다.

---

## 1. 문서 오너십 원칙

| 구분 | 오너 | 내용 |
|---|---|---|
| 문서 체계(폴더 구조, 네이밍) | PM | 이 가이드라인 자체 |
| 문서 내용의 품질 기준 | 각 담당 역할 | 예: 기획 문서 내용은 기획, 스크립트 설명서는 프로그래밍 |
| 문서가 최신 상태인지 관리/독촉 | PM | 방치된 초안, 오래된 내용 등 점검 |

> PM은 '어떻게 쓸지'의 틀을 정하고, 각 역할은 '무엇을 쓸지'의 내용 품질을 책임집니다.

---

## 2. 폴더 구조 규칙

```
Docs/
 ├─ {Category}/           예: Design, Technical, Art, Production
 │   └─ {SubFolder}/       예: CharacterControls, Milestone, QATest
 │       └─ {문서명}.md    ← 항상 최신 내용 (단일 파일, 버전 파일 없음)
 └─ README/
     └─ README.md
```

- 문서마다 `{문서명}.md` 파일 하나만 유지하며, 항상 최신 내용을 담습니다.
- 문서를 수정하면 **커밋 메시지에 어떤 내용을 바꿨는지 남기고 커밋**합니다. 과거 내용은 이 커밋 히스토리로 확인합니다.
- 새 카테고리/서브폴더가 필요하면 반드시 PM과 상의 후 생성합니다. (구조가 무분별하게 늘어나는 것 방지)

## 2-1. 카테고리 분류 기준

새 문서를 작성할 때 어느 카테고리(`Design`, `Technical`, `Art`, `Production`)에 넣을지는 아래 기준으로 판단합니다.

| 카테고리 | 분류 기준 | 예시 |
|---|---|---|
| **Design** | "무엇을 만들지" — 게임플레이, 콘텐츠, 수치, 흐름을 정의하는 문서 | 기획서, 캐릭터 스펙, 레벨디자인, 사운드 큐 |
| **Technical** | "어떻게 구현할지" — 엔진/코드/에셋 관리 방식을 정의하는 문서 | 기술기획서, 네이밍 규칙, 라이선스, 스크립트 설명서 |
| **Art** | 시각적 스타일과 리소스 기준을 정의하는 문서 | 아트스타일 가이드 |
| **Production** | 프로젝트 진행/관리와 관련된 문서 (일정, 역할, QA, 할일) | 역할분담, 마일스톤, QA 계획서, ToDoList |
| **README** | 프로젝트 전체를 처음 접하는 사람을 위한 진입점 | README |

**판단이 애매한 경우** (예: 레벨 디자인용 타일맵 규칙이 Design인지 Technical인지):
- "플레이어가 경험하는 내용"이면 **Design**
- "만드는 사람이 지켜야 할 구현 규칙"이면 **Technical**
- 그래도 애매하면 PM과 상의 후 결정

## 2-2. 문서 분리 기준 (하나의 문서에 얼마나 많은 내용을 담을지)

**원칙: 한 문서 = 하나의 명확한 주제/책임 범위**

"한 문서 당 한 내용만"을 너무 좁게 해석하면 문서가 과도하게 파편화되어 오히려 찾기 어려워집니다. 아래 기준으로 하나의 문서로 묶을지, 별도 문서로 분리할지 판단합니다.

### 한 문서로 묶는 경우
- 서로 **함께 변경되는 게 자연스러운 내용** (예: 캐릭터의 이동/점프/코요테타임처럼 서로 의존적인 수치)
- 같은 담당자가 같은 시점에 함께 검토하는 내용

### 별도 문서로 분리하는 경우
- **담당자(역할)가 다른 경우** — 예: 사운드 큐 리스트(기획) vs 스크립트 설명서(프로그래밍)
- **변경 주기가 크게 다른 경우** — 예: 핵심 기획서(자주 변경)와 확장 기능 기획서(MVP 이후 별도로 진화)
- **문서의 목적(성격)이 다른 경우** — 스펙 문서(수치/규칙 정의) / 리스트 문서(목록형) / 관리 문서(일정, 역할, QA)는 성격이 다르므로 분리

### 실제 적용 예시 (현재 프로젝트 기준)
- `CharacterControls`: 이동+점프+코요테타임을 한 문서에 — 서로 의존적인 수치라 함께 관리
- `Core`(기획서) vs `PlusContents`(확장기능): 필수 vs 선택으로 성격이 달라 분리
- `DivisionOfRoles`, `Milestone`, `QATest`, `ToDoList`: 각각 독립적으로 갱신되는 관리 문서라 분리

### 판단이 애매할 때
- "이 두 내용이 항상 같이 바뀌는가?" → 그렇다면 합치기
- "이 내용을 찾는 사람이 다른 내용도 같이 볼 필요가 있는가?" → 아니라면 분리
- 그래도 애매하면 PM과 상의 후 결정

## 3. 네이밍 규칙

- 문서명은 한글 스네이크/언더스코어 조합 사용 (예: `캐릭터컨트롤_스펙.md`)
- 문서명은 한 번 정하면 가급적 변경하지 않습니다. (README 링크가 깨지는 원인)

---

## 4. README 링크 규칙

- README에서 문서를 링크할 때는 반드시 실제 파일 경로(`Docs/{Category}/{SubFolder}/{문서명}.md`)를 가리킵니다.
- 새 카테고리/문서를 추가하면 README의 문서 목록도 함께 갱신합니다. (PM 책임)

---

## 5. 문서 작성/리뷰 프로세스

1. 담당 역할이 초안 작성
2. 관련 역할(예: 스펙 문서는 기획+프로그래밍)과 짧게 리뷰
3. 확정되면 PM이 README 링크 갱신 여부 확인
4. 회의에서 결정된 변경 사항은 회의록에도 함께 남기는 것을 권장
5. 문서를 수정했다면 GitHub에 커밋해 변경 이력을 남깁니다. (과거 내용 확인은 커밋 히스토리로 가능)

---

## 6. 필수 문서 카테고리 (최소 기준)

| 카테고리 | 필수 문서 |
|---|---|
| Design | 게임 기획서, 기능/캐릭터 스펙, 레벨디자인 |
| Technical | 기술기획서, 에셋 네이밍 규칙, 라이선스 관리, 스크립트 설명서 |
| Art | 아트스타일 가이드 |
| Production | 역할분담, 일정/마일스톤, QA 계획서, ToDoList |
| README | 프로젝트 개요 및 전체 문서 목록 |

프로젝트 성격에 따라 회의록, 이슈 로그, 빌드 노트, 회고 등은 PM 판단 하에 추가할 수 있습니다.

## 8. 문서 폐기(삭제) 규칙

문서가 더 이상 필요 없어졌을 때(내용이 무효화됨, 기능이 취소됨 등) 처리하는 규칙입니다.

1. 루트의 `{문서명}.md` 파일을 삭제합니다. (삭제 전 내용은 GitHub 커밋 히스토리에 그대로 남으므로 별도 백업 불필요)
2. 삭제 커밋 메시지에 삭제 사유를 남깁니다. (예: "기능이 취소됨", "다른 문서로 통합됨")
3. README.md에서 해당 문서를 가리키던 링크/항목을 함께 제거합니다. (README 링크가 깨지지 않도록 필수)
4. 다른 문서에서 이 문서를 참조하고 있었다면, 해당 참조도 함께 확인/수정합니다.
